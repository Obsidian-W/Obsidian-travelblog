# Repository instructions

For article work, read `docs/QUALITY-RULES.md` before editing. Follow the user's current instructions and preserve their existing edits.

## Match existing articles before writing

- Read the live target file and its current diff first.
- Read the corresponding sections of two relevant existing articles. For China itinerary summaries, start with `Itinerary-Yunnan.md` and `Itinerary-PearlDelta.md` under `site/content/english/blog/`.
- Establish the reference structure, exact section names, destination grouping and length of descriptions before drafting. Do not invent a new format when the user asks to match existing articles.
- Keep itinerary summaries brief: destination groups and actual sights. Put transport instructions, prices, booking details and explanations in the detailed sections.
- Preserve the user's section names. Do not rename sections to solve a formatting or content complaint.

## Check the whole requested section

- Apply a correction to every occurrence of the same problem within the requested scope. Do not wait for the user to identify each row or sentence.
- For itinerary summaries, check day coverage, duplicate destinations, base towns, nearby sights and consistency with the detailed route. Exclude flights and extra-day rows when the user has rejected them.
- Remove generic filler, obvious reminders, defensive caveats and commentary about how the article was drafted. Keep necessary uncertainty concise; never turn an estimate into a verified fact.
- Preserve author opinions, firsthand details, updated prices, image placement and unrelated content. Re-read the live file immediately before saving so concurrent edits are not overwritten.

## Completion requires evidence

- Read the saved file and the diff of this edit. Compare the entire changed section directly with the reference sections and the user's corrections.
- A successful build only proves that the site builds. It does not prove that wording, grouping or content meets the request.
- Report only checks actually performed. Do not say that a section is fixed merely because a replacement command succeeded.
- If corrected twice on the same issue, stop making isolated patches. Re-read the live section, references and corrections; identify the mistaken assumption; then make one coherent correction within the authorised scope.
- If the requested result is still unclear after checking the references, ask one precise question instead of guessing repeatedly.
